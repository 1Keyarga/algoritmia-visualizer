1. Introducción
1.1 Propósito
Este documento especifica los requisitos funcionales y no funcionales del Visualizador Interactivo de Algoritmos basado en Gamificación, conforme al estándar ISO/IEC/IEEE 29148:2018. Constituye la formalización del resultado esperado R2.1 del proyecto, tomando como punto de partida el bosquejo preliminar de catorce requisitos funcionales (RF-01 a RF-14) definido en la etapa de análisis pedagógico, y ampliándolo con los requisitos adicionales necesarios para una especificación completa: requisitos funcionales complementarios (RF-15 a RF-17), requisitos no funcionales, requisitos de interfaz, actores, casos de uso y la matriz de trazabilidad correspondiente.
El documento está dirigido al equipo de diseño y desarrollo del proyecto, y sirve como base para el diseño de la arquitectura del sistema, la construcción de prototipos de alta fidelidad (R2.2) y la implementación de la plataforma web (R3.1).
1.2 Alcance del sistema
El sistema comprende una plataforma web de visualización interactiva de algoritmos orientada a estudiantes de una facultad de ingeniería de una universidad privada peruana. El alcance incluye:
Visualización paso a paso de algoritmos de las familias de ordenamiento, búsqueda y divide y vencerás.
Sincronización entre pseudocódigo, estado de variables y representación gráfica de la estructura de datos.
Mecanismos de interactividad pedagógica: predicción de estados, retos de completar el algoritmo, tutorial guiado y construcción manual de estructuras.
Mecánicas de gamificación basadas en el modelo Octalysis (Logro, Empoderamiento, Escasez): retos progresivos, retroalimentación inmediata y avance condicionado al dominio del contenido.
Comparación simultánea de dos algoritmos sobre un mismo conjunto de datos.
El alcance NO incluye:
Aplicaciones móviles nativas para Android o iOS.
Compilación o ejecución real de código fuente en algún lenguaje de programación.
Algoritmos de grafos, programación dinámica, inteligencia artificial o computación paralela.
Integración con sistemas institucionales de gestión académica o plataformas LMS.
Un panel de administración o reportería para docentes dentro de la propia plataforma.

2. Descripción general
2.1 Perspectiva del producto
El visualizador es un sistema nuevo, autocontenido y de tipo cliente (client-side). No reemplaza ni se integra con ningún sistema institucional existente (LMS, sistema de gestión académica); opera como una aplicación web independiente desarrollada con React.js y TypeScript para el frontend, y D3.js para la representación gráfica de las estructuras de datos y sus transiciones. La lógica de simulación de cada algoritmo (motor de trazado) se ejecuta enteramente en el navegador del estudiante, sin requerir un backend para el funcionamiento del núcleo de visualización. La plataforma se despliega sobre infraestructura de hosting gratuita.
2.2 Funciones del producto
A alto nivel, el sistema debe permitir:
Ejecutar y controlar paso a paso la animación de un algoritmo, sincronizada con su pseudocódigo y el estado de sus variables (núcleo de visualización).
Comparar el comportamiento de dos algoritmos sobre el mismo conjunto de datos.
Involucrar activamente al estudiante mediante predicciones, retos y construcción manual de estructuras (interactividad pedagógica).
Motivar la progresión del estudiante mediante mecánicas de gamificación (niveles, retroalimentación inmediata, registro de intentos).

2.4 Entorno operativo
Navegadores soportados: dos últimas versiones estables de Chrome, Firefox y Edge.
Dispositivos: computadoras de escritorio o laptop con mouse/teclado, en resolución mínima de 1280×720 (fuera de alcance el soporte táctil/móvil nativo).
Conexión a Internet requerida únicamente para la carga inicial de la aplicación; la ejecución de los algoritmos no requiere conexión continua.
2.5 Restricciones de diseño e implementación
La implementación debe usar React.js, TypeScript y D3.js, conforme a la arquitectura tecnológica definida para el proyecto.
El despliegue debe realizarse sobre servicios de hosting gratuitos, lo cual impone límites de disponibilidad y de recursos de cómputo/almacenamiento.
Los algoritmos incluidos se limitan a las familias de ordenamiento, búsqueda y divide y vencerás, conforme al alcance definido.
2.6 Supuestos y dependencias
Se asume que los estudiantes cuentan con acceso a un navegador moderno y conexión a Internet durante las sesiones de uso y evaluación.
Se asume que la muestra de evaluación (pretest/postest) corresponde a estudiantes de la facultad de ingeniería de la universidad privada considerada, sin pretender generalizar los resultados a otras poblaciones.
El proyecto depende de la validación de los instrumentos de pretest/postest por parte de expertos (R3.2) para la etapa de evaluación.
3. Requisitos específicos
3.1 Requisitos de interfaces externas
3.1.1 Interfaces de usuario
La interfaz debe seguir un diseño web de escritorio, organizado por módulos (núcleo de visualización, predicción y retos, tutorial guiado, recursión), con divulgación progresiva de paneles (p. ej., el Global frame permanece colapsado salvo en algoritmos recursivos). Todo estado representado por color debe contar con un indicador no cromático adicional (RNF-07).
3.1.2 Interfaces de hardware
No aplican interfaces de hardware específicas; el sistema requiere únicamente un dispositivo con navegador web, mouse y teclado.
3.1.3 Interfaces de software
El sistema se implementa como una aplicación web (React.js 18+, TypeScript, D3.js v7) ejecutada íntegramente en el navegador del cliente. No se especifican interfaces con bases de datos u otros sistemas de software en el alcance actual.
3.1.4 Interfaces de comunicación
La comunicación entre el navegador y el servidor de hosting se realiza mediante HTTPS, únicamente para la carga de los recursos estáticos de la aplicación. No se requieren interfaces de comunicación en tiempo real (websockets) para el funcionamiento del núcleo, dado que la simulación del algoritmo ocurre en el cliente.
3.2 Requisitos funcionales
Los requisitos RF-01 a RF-14 formalizan el bosquejo preliminar (Tabla 13 del documento de proyecto), el cual el propio proyecto reconoce como "un listado no exhaustivo" y "una visión global", no como la lista final de requisitos. Los requisitos RF-15 a RF-17 se incorporan como complemento necesario, identificados durante el diseño de interfaz y a partir del modelo de gamificación. Los requisitos RF-18 a RF-24 se incorporan a partir de un benchmarking de herramientas de visualización algorítmica de referencia (apartado 3.2.1), para completar la especificación exigida por el resultado R2.1.
3.2.1 Requisitos identificados mediante benchmarking de herramientas similares
Con el fin de ampliar el bosquejo preliminar más allá de lo definido inicialmente, se compararon las funcionalidades del visualizador propuesto contra tres referentes reconocidos en la literatura y la práctica de visualización algorítmica: VisuAlgo (Halim, 2011), una plataforma con más de una década de uso académico en cursos universitarios de estructuras de datos; Python Tutor (Guo, 2013), la herramienta de visualización de ejecución de código más utilizada en cursos introductorios de programación a nivel mundial; y los patrones de diseño comunes observados en implementaciones open-source de visualizadores de algoritmos de ordenamiento. 3.3 Requisitos no funcionales
ID
Categoría
Descripción
Criterio de verificación
RNF-01
Usabilidad
La interfaz debe cumplir con los principios de usabilidad de Nielsen y con las pautas WCAG 2.1 nivel AA en lo referente a contraste de color, dado que RF-05 depende de un código de colores semántico.
Evaluación heurística + prueba con lector de contraste (mínimo 4.5:1).
RNF-02
Rendimiento
La animación paso a paso debe renderizarse a un mínimo de 30 fps y la transición entre pasos no debe superar los 150 ms, incluso con conjuntos de datos de hasta 50 elementos.
Prueba de rendimiento con DevTools (Performance panel) en los tres navegadores soportados.
RNF-03
Confiabilidad
El 100% de las simulaciones algorítmicas incluidas en el alcance deben ejecutarse de manera correcta y libre de errores, verificado mediante casos de prueba funcionales.
Suite de pruebas automatizadas que compare la traza generada contra el resultado esperado de cada algoritmo.
RNF-04
Portabilidad / compatibilidad
La plataforma debe operar correctamente en las dos últimas versiones estables de Chrome, Firefox y Edge, sin requerir instalación de software adicional.
Prueba manual de compatibilidad cruzada (cross-browser testing).
RNF-05
Disponibilidad
La plataforma, al estar desplegada sobre infraestructura de hosting gratuita, debe estar disponible al menos el 95% del tiempo durante el periodo de evaluación con estudiantes.
Monitoreo de disponibilidad durante el periodo de aplicación del instrumento pretest/postest.
RNF-06
Mantenibilidad
El código fuente debe organizarse en componentes reutilizables (React) documentados, de modo que un nuevo algoritmo pueda incorporarse sin modificar el motor de trazado existente.
Revisión de código y verificación de que el repositorio incluya documentación técnica (README, comentarios de arquitectura).
RNF-07
Accesibilidad
Todo estado representado únicamente por color (RF-05) debe contar con un indicador visual alternativo no cromático, para estudiantes con daltonismo.
Prueba con simulador de daltonismo (deuteranopía y protanopía) sobre las pantallas del núcleo.
RNF-08
Seguridad de datos
Los datos recolectados mediante los instrumentos de pretest/postest (Google Forms) deben tratarse de forma anónima o seudonimizada, sin exponer información personal identificable en los reportes del proyecto.
Revisión del diseño del instrumento y del tratamiento de datos frente a la política de protección de datos aplicable.

4. Enfoque de verificación
La verificación de los requisitos funcionales se realiza mediante casos de prueba funcionales que comparan el comportamiento observado de la plataforma contra la traza real generada por el motor de simulación de cada algoritmo, exigiendo que el 100% de las simulaciones incluidas en el alcance se ejecuten de manera correcta (RNF-03), conforme al criterio de aseguramiento de calidad definido en el proyecto.
La verificación de los requisitos no funcionales de usabilidad y accesibilidad (RNF-01, RNF-07) se realiza mediante evaluación heurística y pruebas con herramientas de simulación de daltonismo, dado que el sistema depende del código de colores semántico (RF-05) como mecanismo central de comunicación visual.
Este documento debe revisarse y actualizarse conforme avance el diseño de prototipos de alta fidelidad (R2.2) y la implementación de la plataforma (R3.1), manteniendo la trazabilidad entre requisitos, objetivos específicos y habilidades de pensamiento algorítmico.
